# Aurora Identity

Status: **Canonical design draft**
Version: **0.1**

Aurora Identity defines how a person is identified, authenticated, and connected to a local Aurora OS profile.

The user-facing concept is intentionally simple: after boot, Aurora shows a single Aurora Key field. The user does not first choose an account icon and does not enter a separate username and password pair.

The first implementation is local and offline-first. Network identity, device synchronization, recovery services, and multi-device federation are future layers built on top of the same stable local identity model.

## 1. Product goal

The default login experience is:

1. Aurora OS finishes booting.
2. A full-screen login surface appears.
3. The screen exposes one primary field: **Aurora Key**.
4. The user enters an alphanumeric key.
5. Aurora normalizes and verifies the key.
6. If the key matches an existing local identity, Aurora starts that user's session.
7. If no local identity matches, Aurora asks whether a new profile should be created with that key.
8. Choosing **Create** begins first-user/profile setup.
9. Choosing **Cancel** returns to the empty Aurora Key field.

The login screen must not enumerate local accounts by default.

## 2. Naming

Canonical user-facing name:

- **Aurora Key** — the secret string typed by the user.

Canonical subsystem name:

- **Aurora Identity** — identity, authentication, session bootstrap, profile binding, and future device federation.

Internal identifiers are deliberately separate from the Aurora Key.

## 3. Core identity model

Each local Aurora identity owns a stable, opaque `user_id` generated by the system.

The Aurora Key is an authentication credential, not the primary database key.

Changing an Aurora Key must therefore never require moving the profile or changing the stable `user_id`.

Conceptual record:

```text
AuroraIdentityRecord
- user_id                  stable opaque identifier
- key_verifier             password/KDF verifier; never plaintext
- key_salt                 unique cryptographic salt
- display_name             optional profile label, never required for login
- profile_path             local profile root
- created_at               creation timestamp
- last_login_at            last successful local authentication
- credential_version       verifier format / migration version
- status                   active / locked / recovery-required / disabled
- failed_attempt_state     rate-limit metadata
```

The first storage backend is expected to be a protected local identity database once Aurora has a persistent filesystem and system service layer.

## 4. Aurora Key format

Aurora Key accepts ASCII letters and decimal digits.

Canonical input normalization:

- lowercase letters are converted to uppercase;
- visual separators such as `-` and spaces may be accepted and ignored;
- separators are presentation only and are not part of the canonical secret;
- the normalized credential consists only of `[A-Z0-9]`;
- normalization must happen before verifier derivation;
- no locale-dependent transformations are permitted.

Recommended initial policy:

- minimum normalized length: **12** characters;
- maximum normalized length: **32** characters;
- generated keys should use cryptographically secure randomness;
- user-created keys are permitted if they satisfy policy;
- the UI may group characters visually, for example `A7K9-M2PQ-84XR`, without altering the normalized key.

The exact policy remains versioned so stronger requirements can be introduced without invalidating existing accounts.

## 5. Security rules

### 5.1 Plaintext prohibition

Aurora OS must never persist the Aurora Key in plaintext.

It must also avoid writing the plaintext key to:

- serial logs;
- kernel logs;
- crash dumps;
- telemetry;
- shell history;
- debug traces;
- UI diagnostics.

Buffers that temporarily hold the credential should be cleared after verification when practical.

### 5.2 Credential verifier

The persistent credential representation must use a modern memory-hard password derivation function.

Target algorithm: **Argon2id** with a unique random salt per identity.

Parameters are stored with the verifier and must be upgradeable over time.

Until Aurora ships its audited cryptographic implementation and secure random source, no placeholder hash is to be described as production authentication.

### 5.3 Constant-time comparison

Verifier comparison must avoid credential-dependent early exit where the cryptographic implementation exposes raw comparison operations.

### 5.4 Rate limiting

Repeated failures must trigger progressive delay / throttling.

The design must prevent an attacker from using the login surface as an unrestricted high-rate local guessing oracle.

Rate-limit state belongs to the identity/authentication service, not to UI widgets.

### 5.5 Account enumeration

The default login surface must not show a list of existing users.

A failed lookup and a failed verifier check should avoid unnecessarily revealing whether a particular candidate identity exists.

The special "user not present" creation flow is permitted only after Aurora has established the local creation policy for that machine. On managed or locked systems, creation may be disabled.

### 5.6 Recovery

Aurora Key recovery is not equivalent to storing a reversible copy of the key.

Future recovery mechanisms may include:

- a separately generated recovery credential;
- trusted-device approval;
- encrypted recovery escrow explicitly enabled by the user;
- administrative recovery on managed systems.

Recovery is a separate credential path and must not weaken the primary verifier.

## 6. Local-first requirement

Aurora Identity must support normal local login with no network connection.

The following must not depend on a cloud service:

- boot;
- Aurora Key verification;
- local user creation when policy allows it;
- local profile opening;
- logout / lock / re-authentication;
- recovery paths that are explicitly local.

Cloud-linked identity can be added later but cannot become a mandatory dependency for ordinary local access.

## 7. Trust boundaries

Aurora OS uses a modular hybrid capability-kernel architecture. Aurora Identity follows that model.

### Kernel responsibilities

The kernel may provide only the mechanisms required for secure identity/session operation, including:

- process and address-space isolation;
- capability enforcement;
- protected IPC;
- secure access to device/input services;
- protected storage capabilities;
- secure random primitive once available;
- session boundary primitives;
- credential-buffer protection mechanisms where practical.

The kernel does **not** own user database policy or login workflow policy.

### User-space Identity Service

A future isolated **Aurora Identity Service** owns:

- identity record storage;
- Aurora Key verifier derivation and checking;
- credential migration;
- failed-attempt throttling policy;
- user creation policy;
- recovery policy;
- mapping authenticated identity to profile/session bootstrap;
- audit events that do not disclose credentials.

### Login UI / Session UI

The login surface owns presentation and input interaction only.

It sends credential material to the Identity Service through a narrow authenticated IPC interface and receives only the result/state required to update the user interface.

The login surface must not receive broad filesystem access merely because it is part of login.

## 8. Authentication state machine

Canonical high-level states:

```text
BOOT_COMPLETE
    -> LOGIN_IDLE
    -> KEY_ENTRY
    -> AUTHENTICATING

AUTHENTICATING
    -> SESSION_STARTING          existing identity verified
    -> CREATION_OFFER            no matching local identity, creation allowed
    -> AUTH_FAILED               invalid credential / verification failure
    -> THROTTLED                 rate limit active

CREATION_OFFER
    -> PROFILE_SETUP             user chooses Create
    -> LOGIN_IDLE                user chooses Cancel

PROFILE_SETUP
    -> SESSION_STARTING
    -> LOGIN_IDLE                cancelled / failed safely

SESSION_STARTING
    -> SESSION_ACTIVE
```

UI code must treat authentication as asynchronous even if the first backend is locally fast.

## 9. Login screen specification

### 9.1 Default composition

The login screen is full-screen and intentionally minimal.

Primary composition:

- Aurora visual background;
- Aurora identity mark / title;
- one centered Aurora Key field;
- a concise helper label;
- status/error area below the field;
- optional small system controls in a secondary region in later versions.

The screen does not show account tiles.

### 9.2 Key field

The field must support:

- keyboard focus by default;
- uppercase visual presentation;
- automatic visual grouping;
- Backspace;
- Enter / submit;
- safe clearing after failed or completed authentication;
- cursor/caret state;
- future accessibility hooks;
- future on-screen keyboard support.

For production authentication the credential should normally be masked or partially masked according to the final UX decision. A temporary development build may expose entered characters only when an explicit debug build flag is enabled.

### 9.3 Unknown identity dialog

Canonical copy:

**User not found. Create a new Aurora profile with this key?**

Actions:

- **Create**
- **Cancel**

The dialog must only appear when local account creation is allowed by machine policy.

### 9.4 Existing identity

On successful verification, the UI transitions directly to session startup. No redundant user-selection screen is inserted.

## 10. Session binding

Successful authentication returns an opaque authenticated-session handle bound to the stable `user_id`.

The session bootstrap component uses that identity to obtain narrowly scoped capabilities for:

- the user's profile root;
- settings;
- desktop/session services;
- user-owned application state;
- per-user secrets through a future protected secret service.

Applications must never receive the Aurora Key.

## 11. Multi-device evolution

The local `user_id` and Aurora Key must not be conflated with a future global account identifier.

A later Aurora Identity federation layer may support:

- linking several Aurora devices;
- encrypted profile/settings synchronization;
- trusted-device enrollment;
- device revocation;
- optional account discovery;
- roaming identity metadata.

A device must still be able to authenticate a local user offline using its local verifier.

## 12. Current repository integration

The current repository already provides:

- a Limine-based x86_64 boot path;
- a 32-bit RGB framebuffer;
- milestone-driven boot UI;
- PMM/VMM;
- GDT/TSS and Ring 3 support;
- capabilities and IPC;
- scheduler and process isolation.

It does not yet provide a persistent filesystem-backed identity store, a complete input subsystem, a compositor, or the final user-space system-service environment.

Therefore Aurora Identity is introduced in phases.

### Phase A — Login surface prototype

Current implementation target:

- add a dedicated `login_ui` module;
- transition from completed Boot UI to the Login UI;
- render a resolution-independent full-screen Aurora Identity page directly to the framebuffer;
- render the Aurora Key field and status region;
- expose a small state API so future keyboard/input code can update it;
- do not implement fake production authentication.

This is a bootstrap prototype. It proves the boot-to-login transition while the compositor and system services do not yet exist.

### Phase B — Input path

- keyboard device discovery / driver service;
- normalized key events;
- focus and text-entry layer;
- connect Login UI to real input;
- preserve architecture isolation so x86_64 keyboard hardware details do not leak into identity policy.

### Phase C — Persistent local Identity Service

- filesystem/service substrate;
- secure random source;
- Argon2id implementation or audited dependency;
- protected local identity database;
- account creation;
- authentication IPC;
- rate limiting;
- secure session handle.

### Phase D — User session

- session manager;
- profile mount/open;
- desktop/compositor startup;
- lock/logout/re-authentication;
- multiple simultaneous or switchable sessions if later required.

### Phase E — Optional federation

- trusted-device model;
- encrypted synchronization;
- optional Aurora network account;
- recovery and device revocation.

## 13. Implementation constraints

1. No plaintext Aurora Key persistence.
2. No user-account enumeration on the default login screen.
3. No mandatory cloud dependency for local authentication.
4. No fake security primitive promoted as production authentication.
5. Authentication policy stays outside the privileged kernel.
6. Hardware-specific input code stays behind architecture/driver boundaries.
7. The stable `user_id` is independent from the Aurora Key.
8. Changing the Aurora Key must not recreate the profile.
9. Login remains responsive and asynchronous.
10. UI appearance can evolve without changing the authentication contract.

## 14. First implementation acceptance criteria

The first repository milestone is accepted when:

- the kernel completes its existing boot self-tests;
- the boot UI reaches 100%;
- control transitions to a dedicated Aurora Identity login surface;
- the login UI is rendered without depending on filesystem, PNG decoding, floating point, or a compositor;
- the layout scales from the current framebuffer dimensions and is usable at the target 1920x1080 resolution with a 1280x720 fallback;
- the code builds with the existing freestanding toolchain;
- no authentication secret is logged or persisted;
- the module boundary allows input/authentication to be connected later without rewriting the boot UI.
